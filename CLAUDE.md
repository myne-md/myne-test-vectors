# myne-test-vectors — JSON test vectors for Myne v0.1 protocol

> Companion repository to [`myne`](https://github.com/myne-md/myne). Licensed **CC-BY-4.0** (Creative Commons Attribution 4.0) — vectors must remain maximally reusable for independent implementations in any language, with attribution to Myne.

> **This repository is PRIVATE, deliberately and for now** (2026-08-13 — the whole `myne-md` org is, while the project is pre-alpha). The licence is already the permissive one; only the visibility bit is closed, and it is closed on purpose rather than by oversight. Two consequences follow, and both are live — they are the price of the decision, not arguments against it:
>
> 1. **No CI gate anywhere runs the byte-level vectors.** The main repo's `vector-verification` step and mobile's `protocol-vectors` step are both commented out, and both give the same reason: cloning a private repo needs a `vectors_token` secret, and a `from_secret:` naming a secret the repo cannot see fails *config-compile*, killing the whole pipeline rather than one step (`.woodpecker.yml`, MYND-635). Today the vectors gate on developer machines only — `cargo test -p protocol --test vectors` at pre-push, with the companion checked out beside the main repo.
> 2. **The "Purpose" paragraph below states a goal, not a present fact.** A port author outside this org cannot fetch these files, so nobody outside has verified the cross-implementation claim. Read that paragraph as the contract this repository is *built to* honour once it opens.
>
> Two ways out when the time comes, and they are not equivalent: **provisioning `vectors_token`** in Woodpecker turns the CI gate back on while keeping the repo closed (fixes 1, leaves 2), whereas **making the repo public** fixes both and needs no secret at all. Until one of them happens, do not let prose in this repo or the main one describe the vector gate as *enforcing* — it enforces on no machine.

## Purpose

Language-agnostic JSON test vectors for the Myne cryptographic protocol. Any independent implementation (Rust, Go, Swift, Kotlin, JavaScript, etc.) MUST produce **bit-identical outputs** from these inputs. A reviewer or contributor verifying a port should not need to read the reference Rust implementation; running their language's test runner against this repository should be enough.

## JSON schema convention

Every vector file:
- Hex-encoded inputs (`key`, `nonce`, `aad`, `salt`, etc.) — lowercase, no `0x` prefix
- Hex-encoded expected outputs
- `spec_section` reference (e.g., `"protocol.md §5.1.1"`)
- `vector_id` (stable string, never reused)
- `protocol_version` — pinned once per file (`"v0.1"` or `"v0.2"`) so vectors for different majors coexist without ambiguity. It is a `const` in each root schema, which is what lets a validator reject a file filed under the wrong version directory instead of silently checking it against the wrong contract

Field naming convention applied across every `cases.json`:
- Identity: `vector_id` (string, format `<category>/<version>/<descriptive-slug>`)
- Discriminator: `case_kind` (optional, present only when a category has more than one case shape)
- Inputs: `input_<semantic>_<encoding>` (e.g., `input_root_key_hex`, `input_plaintext_utf8_hex`)
- Expected outputs: `expected_<semantic>_<encoding>` (e.g., `expected_subkey_hex`, `expected_prefs_blob_hex`)
- Failure-mode expectation: `expected_kind` (string, e.g., `aead_fail`)
- Informational / intermediate: `informational_<semantic>[_<encoding>]` (suffix optional for structured objects)

The canonical machine-readable contract lives at `schema/<version>.json` (top-level shape) and `schema/<version>/<category>.json` (per-category case shape), one pair per protocol version. Each root dispatches via `oneOf` keyed on the `schema` field.

## Next-major (v0.2) vectors

v0.2 vectors live under `vectors/<cat>/v0.2/` beside `v0.1/`, validated by their own `schema/v0.2.json` + `schema/v0.2/`. **The two roots are separate documents, not an inheritance chain**: `protocol_version` is a `const` in each, which is exactly the pin that makes a version's shape checkable — one schema spanning both majors would have to relax it. A v0.2 file is therefore INVALID against the v0.1 root by construction, and the validation loop derives the root from the directory name so it can never check one against the other.

Frozen and vectored today: AAD prefix `"myne.v0.2|"`, HKDF context prefix `"myne.v0.2 "`, header `protocol_version` byte `0x02`, per-note magic `NC05`, plus the `NTV5` / `MYT5` envelopes. Each is a major-version-event constant in the main repo's root `CLAUDE.md`.

v0.1 and v0.2 are **forward-incompatible by design** — no extension points, no algorithm-agility headers — and share this repository for distribution convenience, not for coexistence within a single client. Cross-major reads happen only through an explicit user-initiated migration (§10.4.1), which is itself what the v0.2 AAD builders exist for.

(The `v005` codename this section used to carry is **retired** — `design notes.md` 2026-08-01. It also claimed magic bytes `MY05` / `MYV5`, which never matched the main repo's reservation table (`NT05` / `NTV5`) and disagreed with the `NTV5` the landed vectors actually pin. Read `v005` in an old `decisions.md` entry as a historical pointer, never as something to implement.)

## Cross-implementation discipline

Independent ports (Phase 2 Go server, Phase 3 web/mobile clients) verify primitive-level compatibility by running these vectors through their language's runner. **A failed vector in any port is a stop-the-world bug** — either the port has drifted or the spec is wrong. Don't regenerate vectors to "fix" a failing port without reading why.

## Common commands

```bash
# Validate every landed cases.json against its canonical sub-schema.
#
# Three shapes here are load-bearing, and each was learned the hard way:
#   * ONE quoted glob for -r, not one flag per sub-schema. ajv-cli 5 accepts
#     exactly one -r; a second is rejected outright as "too many arguments",
#     so a per-file loop reports EVERY category invalid and reads like 51
#     broken vector files rather than one broken invocation.
#   * ONE category per run (-d inside the loop). A combined all--d run has
#     tripped a false-negative through a schema oneOf artefact.
#   * The VERSION comes from the directory name and selects its own root
#     schema. This loop said `v0.1` literally until the first v0.2/ landed,
#     and those files were then validated by nothing at all — in the one
#     repository whose entire job is to be the gate. They could not have been
#     checked against the v0.1 root either: protocol_version is a const there.
#     A new version directory with no schema/<version>.json fails the loop
#     rather than being skipped, which is the point of this shape.
# `.woodpecker.yml` + `lefthook.yml` run exactly this; keep the copies in step.
for d in vectors/*/v*/cases.json; do
  ver=$(basename "$(dirname "$d")")
  npx -y ajv-cli@5 validate \
    -s "schema/$ver.json" \
    -r "schema/$ver/*.json" \
    -d "$d" \
    --spec=draft2020
done

# Inspect a single case via jq:
jq '.cases[0]' vectors/hkdf-sha256/v0.1/cases.json
```

## Gotchas

- **NFKD normalization order matters** for BIP-39 phrase vectors — apply NFKD before passing to Argon2id, never after. Vectors must include both NFC and NFKD-equivalent inputs to catch implementations that skip the normalization step.
- **Hex encoding is lowercase, no `0x` prefix.** A vector's `expected_<output>_hex` of `1a2b3c...` not `0x1A2B3C...`. Don't mix cases within a single vector file.
- **Vector IDs are immutable** — once a vector is shipped, its `vector_id` is part of the contract; downstream test runners may reference it. Renaming requires a major version bump.
- **Bit-identical means byte-identical** — there is no "approximately equal" for these vectors. Endianness, padding, and reserved bytes all matter. Cross-language tests should diff bytes, not parsed structures.
- **Adding a new category** requires landing a sub-schema file under `schema/v0.1/`, extending the root schema's `schema` enum AND `oneOf` branches in lockstep, and adding the corresponding `cases.json` + integration runner in the main repo.
